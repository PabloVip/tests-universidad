Sección 1.1 - Sistemas de Información

El Sistema de Información (SI)

Un SI es la convergencia orquestada de procesos, normativas, tecnologías, actores y datos. Permite capturar, transformar, almacenar y distribuir información útil para la operación y el control de una organización.

La base de datos no es solo tecnología aislada: es la memoria institucional, el soporte crítico de los procesos organizacionales.

La BD provee a esos procesos:

  • Persistencia
  • Consistencia (integridad)
  • Trazabilidad
  • Recuperación
  • Acceso concurrente

Reglas de negocio: constraints, triggers y procedimientos

  • Reglas simples → se incrustan en la BD mediante constraints: PK, FK, UNIQUE, CHECK, NOT NULL (mapeo declarativo y estructural).
  • Reglas complejas o dinámicas (lógica paso a paso) → Triggers y Procedimientos.
  • No delegar las validaciones solo a la aplicación: las apps son efímeras y propensas a fallos.
  • Las constraints son el escudo de gobierno corporativo que defiende la integridad de los datos.
Las constraints son el insumo principal del CBO (optimizador basado en coste): el diseño es rendimiento.
CREATE TABLE empleados (
  id INT PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  edad INT CHECK (edad >= 18),
  salario DECIMAL(10,2) CHECK (salario >= 0)
);

Flujo del dato: Dato → Información → Conocimiento → Decisión → Control

  • Dato: hecho elemental registrado (ej. "120 cafés helados"). Por sí solo no tiene sentido.
  • Información: dato situado en contexto, interpretado y relacionado (ej. dónde, cuándo y cómo se vendieron).
  • Conocimiento: a partir de múltiples informaciones se reconocen patrones útiles (ej. "si la temperatura supera 30 °C, las ventas de café helado suben un 60%").
  • Decisión: actuar sobre ese conocimiento (ej. programar un barista extra).
  • Control: acción estratégica basada en análisis (BI) para verificar si las decisiones producen lo esperado.
La confiabilidad del Business Intelligence depende enteramente del motor transaccional que gestiona el DBA. Un dato contaminado contamina toda la cadena: información defectuosa → conocimiento deformado → malas decisiones → control evaluando una realidad falsa.

El DBA opera en un entramado socio-técnico: necesita profundidad técnica y capacidad de interlocución para diagnosticar incidentes y comunicarse con los demás perfiles.

El costo del fallo, RTO y RPO

Los fallos suelen deberse a:

  • Concesión de privilegios excesivos
  • No registrar cambios o no seguir procedimientos
  • Operar en entornos equivocados
  • Ingreso de datos inconsistentes (mal diseño)
La mala gestión deja de ser un problema técnico y se convierte en crisis corporativa: el downtime tiene coste financiero y daño reputacional.
MétricaDefinición
RTO (Recovery Time Objective)Tiempo máximo que el sistema puede estar caído antes de que el daño sea inaceptable.
RPO (Recovery Point Objective)Pérdida de datos máxima tolerable tras un incidente (minutos / horas / días).

Si un negocio exige RTO ≈ RPO ≈ 0 (banca, UCI, procesadores de pago) se traduce en Maximum Availability Architecture (MAA).

  • Maximum Protection: RPO ≈ 0, prioriza los datos sobre la disponibilidad.
  • Maximum Performance: RPO > 0, prioriza el rendimiento arriesgando datos.

Sección 1.2 - Pensamiento de Sistemas

Independencia de datos

TipoQué permiteCómo se logra
Independencia físicaModificar la estructura física de almacenamiento (mover archivos a discos más rápidos) sin reescribir las aplicaciones.No altera la visión lógica.
Independencia lógicaAlterar el esquema conceptual (tablas, columnas, relaciones) sin romper las aplicaciones.Vistas, APIs, procedimientos o capas de acceso.

Calidad e integridad del dato

Calidad del dato = preguntarse si, para el proceso de negocio, el dato es:

  • Correcto: coincide con el hecho real.
  • Completo: no falta ningún dato necesario.
  • Coherente: compatible con el resto de la información.
  • Oportuno: llega a tiempo para decidir.
  • Trazable: se sabe de dónde procede, quién lo modificó y qué cambios se hicieron.
  • Adecuado: sirve para la finalidad del uso concreto.

La integridad, mediante diseño, restricciones y control, protege la coherencia interna del dato.

ILM (Information Lifecycle Management)

Los datos tienen fecha de caducidad operativa: su valor y frecuencia de acceso cambian, y la infraestructura debe reflejarlo económicamente.
  1. Creación y uso (Activo): alto valor operativo → almacenamiento de alto rendimiento.
  2. Disminuye uso (Histórico): se mantiene el valor legal/histórico.
  3. Menor actividad (Archivo): se traslada a almacenamiento económico.
  4. Termina la retención (Purga): eliminación según la política de retención (cómo conservar, cuánto tiempo y qué pasa al terminar).

Deuda técnica y anomalías (falta de normalización)

Un esquema relacional deficiente acumula fragilidades: duplicaciones, incoherencias, ambigüedad semántica y consultas cada vez más costosas → anomalías:

  • Anomalía de inserción: no se puede registrar un hecho sin inventar/duplicar otro.
  • Anomalía de actualización: un cambio requiere un UPDATE masivo en múltiples lugares (bloquea miles de filas).
  • Anomalía de borrado: eliminar un registro arrastra información valiosa que se pierde (ej. perder el contacto del proveedor al borrar su último producto).
El diseño relacional normalizado es la única defensa estructural contra estas corrupciones operativas. En Data Warehousing sí es habitual desnormalizar deliberadamente para facilitar determinadas consultas analíticas.

Sección 1.3 - Bases de Datos y SGBD

Qué es una base de datos

Una BD es una colección estructurada y persistente de datos relacionados, diseñada para:

  • Representar una parte significativa de la realidad
  • Permitir almacenamiento, consulta, modificación y control

No es una simple acumulación de registros: es una construcción modelada que expresa aspectos del mundo de forma consistente y útil.

Características: organización lógica (esquema lógico separado del físico), persistencia (backups y logs ante cortes), compartición multiusuario (bloqueos y colas), capacidad de consulta (dices qué, no cómo), control de integridad y posibilidad de evolución estructural.

Qué es un SGBD (DBMS)

Es el software especializado que permite definir, mantener, consultar, asegurar, optimizar y recuperar la BD. Actúa como capa de abstracción e intermediación entre aplicaciones/usuarios y los archivos físicos en disco.

Servicios mínimos:

  • Lenguajes de definición y manipulación (DDL / DML, CRUD)
  • Gestión de metadatos (diccionario de datos / catálogo)
  • Control de concurrencia (bloqueos y transacciones)
  • Mecanismos de recuperación (logs para deshacer operaciones incompletas)
  • Seguridad y control de acceso
  • Optimización de acceso (optimizador de consultas)

Anatomía del SGBD: motor de almacenamiento

Storage Manager: transforma las estructuras lógicas en representaciones físicas eficientes en medios persistentes. Decide organización de páginas/bloques, disposición de registros, índices, compresión e interacción con el sistema de archivos.

  • Multi-engine: MySQL, MariaDB, Apache Derby (InnoDB, MyISAM, Aria…).
  • Arquitectura única integrada: Oracle Database, PostgreSQL, MS SQL Server, SQLite.

Motor de consultas: fases

SQL es una especificación declarativa: el usuario dice qué quiere, el sistema decide cómo. Entre lo escrito y lo ejecutado hay una gran distancia arquitectónica.
  1. Lexer: análisis léxico (convierte la sentencia en tokens).
  2. Parser: análisis sintáctico (valida la gramática/orden de tokens).
  3. Validación: significado respecto al catálogo y permisos.
  4. Transformación lógica: subquery unnesting, eliminación de joins redundantes, constant folding, etc.
  5. Optimización por coste (CBO).
  6. Plan de ejecución y ejecución (acceso, filtrado, unión, ordenación, agregación).
En SELECT * FORM clientes el lexer no detecta ningún error (los tokens son válidos); es el parser quien marca el error sintáctico porque no encuentra la palabra FROM.

Gestor de transacciones y concurrencia

Preserva consistencia y aislamiento con varias sesiones concurrentes: delimita transacciones, coordina commit/rollback, gestiona bloqueos, previene conflictos. Se complementa con el Recovery Manager (logging, operaciones Undo/Redo y checkpoints) para la durabilidad.

MVCC = Multi-Version Concurrency Control: versionado de datos con niveles de aislamiento (RC, RR, Serializable) para controlar la concurrencia sin sacrificar orden.

Catálogo, metadatos y diccionario de datos

El SGBD guarda datos sobre sus propios datos: tablas, columnas, restricciones (CHECK, NOT NULL, UNIQUE), usuarios, vistas, índices y relaciones estructurales (PK, FK).

Esta capacidad convierte al SGBD en un sistema reflexivo: puede describirse a sí mismo. Necesario para validar consultas, controlar permisos, optimizar y administrar estructuras.

Almacenamiento simple vs gestión transaccional

CaracterísticaSimple (CSV, JSON, XLSX)Transaccional (SGBD)

La BD como activo crítico de negocio: 4 pilares

  • Memoria organizacional: histórico completo de interacciones, finanzas y operaciones.
  • Evidencia operativa y legal: única prueba auditable de transacciones y cumplimiento.
  • Continuidad funcional: si la BD se detiene, el negocio se paraliza.
  • Motor analítico: materia prima de la inteligencia de negocio.

Sección 1.4 - Evolución del Rol del DBA

Resiliencia y evolución a gran escala

El nuevo DBA no solo gestiona "sistemas que guardan datos"; gobierna infraestructuras que garantizan la viabilidad operativa, legal y financiera del negocio. La pregunta clave evoluciona a:

  • Resiliencia: sobrevivir a fallos sin perder datos.
  • Evolución a gran escala: crecer en capacidad, usuarios y complejidad de forma sostenible.

Responsabilidades operativas y de continuidad

ÁreaQué implica
1. OperacionesDespliegue de entornos, parcheo, migraciones, monitoreo.
2. Capacity Planning predictivoModelar el crecimiento transaccional para provisionar CPU, memoria e IOPS antes de que el motor sufra.
3. SeguridadPrincipio de menor privilegio; trazar cada mutación DDL. Un usuario de aplicación manipula datos (DML), nunca cambia esquemas (DDL).
4. Auditoría y gobiernoMonitoreo en tiempo real, cifrado en reposo y en tránsito, trazabilidad (GDPR, ISO 27001, PCI-DSS).
5. TuningRAM/caché/hilos, query profiling, Lock Management (deadlocks), planes de ejecución, índices y particiones.
6-7. Continuidad y recuperabilidadBackups automatizados con regla 3-2-1, simulacros de DR midiendo RPO y RTO.
IOPS = operaciones de entrada/salida por segundo (no es lo mismo que el ancho de banda, que se mide en MB/s). Si no hay suficiente RAM aumentan las IOPS, la CPU espera al disco, se acumulan consultas en cola y la latencia se dispara.

IaC (Infraestructura como Código) y automatización

  • Despliegues reproducibles: toda la configuración se escribe como código (Terraform, Kubernetes) → clon exacto al instante.
  • Reducción del riesgo humano: nadie toca producción a mano; los cambios pasan por tuberías CI/CD que los prueban primero.
  • Trazabilidad forense: cada cambio es código en el historial (Git) → se sabe quién, qué y cuándo.
El mayor peligro para una BD es un humano tecleando un comando por error en el servidor equivocado.
Al gestionar la BD con código, el trabajo del DBA se fusiona con el del Ingeniero de Plataforma y el SRE (Site Reliability Engineer).

Perfil T-Shaped de alto nivel

  • Eje vertical (especialización profunda): dominio del motor — memoria (buffer pools), bloqueos, índices (Árboles B+), logs transaccionales.
  • Eje horizontal (conocimiento transversal): kernel del SO, redes, lenguajes, orquestación, almacenamiento distribuido.
  • Visión estratégica y comunicación: traducir problemas técnicos en riesgos financieros medibles ante la alta dirección.

Topologías de despliegue

  • On-Premise: control total (microsegundos de latencia, kernel tuning, air-gapped).
  • Cloud: agilidad y elasticidad; transforma CapEx en OpEx; exige FinOps.
  • Geo-distribuidos: coordinación entre nodos, split-brain y latencia de la luz.

En DBaaS no se elimina al administrador: la responsabilidad sobre el dato siempre es del cliente.

Teorema de CAP

En un sistema distribuido es imposible garantizar Consistencia (C) + Disponibilidad (A) + Tolerancia a Particiones (P) simultáneamente. Cuando la red falla, se elige:

  • CP (ej. MongoDB, HBase): rechaza peticiones antes que entregar datos desactualizados (el cajero sin conexión da error antes que un saldo falso).
  • AP (ej. Cassandra, DynamoDB): responde con los datos que tiene aunque estén desactualizados (consistencia eventual).
Los relacionales distribuidos tienden a ser CP; los NoSQL nativos de la nube tienden a ser AP. Un motor local (sin clúster) no sufre particiones y goza de C+A.

Tendencias: IA y semántica

  • BD autónomas (IA integrada): auto-tuning y self-healing. No sustituyen al DBA; elevan su rol hacia estrategia arquitectónica, normativa, FinOps y gobernanza.
  • BD vectoriales + RAG: transforman texto en embeddings y recuperan por similitud matemática/geométrica (coseno, kNN), buscando significado.

Sección 1.6 - Ingeniería Profesional

Cultura de la evidencia y línea base

No se ejecutan instrucciones a ciegas: lo que no puede auditarse y reproducirse no es apto para producción.

Baseline (estado inicial): antes del primer comando se capturan métricas de consumo y registros de error. Si el motor corre nativo (sin contenedores), la evidencia debe incluir logs del kernel y CPU/RAM del anfitrión.

$ free -h > 01_baseline_recursos.txt
$ top -b -n 1 | head -n 15 >> 01_baseline_recursos.txt

Telemetría activa: registrar latencias, bloqueos y planes de ejecución para contrastar el antes y el después de la intervención.

Documentación como código: Markdown y GitOps

  • Inmutabilidad criptográfica: el historial de Git deja rastro imborrable de cada decisión (la "caja negra" del sistema).
  • Reproducibilidad estricta: la bitácora debe ser una receta que cualquier otro ingeniero pueda seguir sin hablar con el autor.

Fases de la metodología del curso:

  1. Inicio del repositorio y trazabilidad (git init, README).
  2. Línea base operativa (docker stats, docker logs).
  3. Conexión y trazabilidad interna (sqlplus, SPOOL, SET TIMING ON).
  4. Telemetría activa (EXPLAIN PLAN, latencia).
  5. Intervención (ej. CREATE INDEX).
  6. Validación matemática (EXPLAIN, latencia, apagar SPOOL).
  7. Documentación y commit (git add, git commit).
Ejemplo real: TABLE ACCESS FULL coste 412 y 2.45 s → crear índice B-Tree → INDEX RANGE SCAN coste 3 y 0.02 s (-99% del tiempo).

Gobierno ético y fideicomiso del dato

El tratamiento de la PII (datos clínicos, financieros, biométricos) se rige por:

PrincipioImplementación técnica
Zero Trust / PoLPAcceso Just-In-Time: nadie consulta datos sensibles sin justificación temporal y criptográficamente auditada.
Data MaskingLos entornos dev/QA jamás contienen PII real: se ofusca preservando integridad referencial y formato.
Auditoría inmutableAlertas automáticas al SOC ante lecturas masivas anómalas.
Cumplimiento como códigoGDPR, PCI-DSS, HIPAA → TDE, Row-Level Security, purgado por caducidad legal.

Estandarización: Runbooks y Playbooks

  • Runbooks: procedimientos deterministas y secuenciales para tareas predecibles (backups, parcheos, rotación de credenciales).
  • Playbooks: árboles de decisión estratégicos para diagnosticar, contener y mitigar incidentes bajo presión.

Cultura Kaizen del dato

Ciclo iterativo: Observar → Medir → Refinar → Automatizar.

  • Los incidentes y caídas son "telemetría no planificada": evidencia para rediseñar índices, ajustar memoria o refinar el modelo.
  • Vigilancia tecnológica activa: evaluar si nuevas cargas justifican BD vectoriales, columnares o autónomas.
