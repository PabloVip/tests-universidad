Sección 2.1 - Oracle como Plataforma Empresarial

Oracle Corporation vs Oracle Database

Oracle Corporation es la empresa tecnológica global. Oracle Database es su producto emblemático: un SGBD relacional destinado a bases de datos de misión crítica (transaccional, multiusuario, seguro, escalable y fuertemente administrable).

Casos de uso 2026

CasoProblema / Ventaja Oracle
1. Core transaccional (Neo-banco)MVCC vía Undo Tablespace: los lectores jamás bloquean a los escritores. RAC redirige la transacción si un servidor explota.
2. JSON Relational Duality (SuperApp)La app ve JSON, pero Oracle lo guarda en tablas relacionales normalizadas: cero duplicación y total ACID.

Ediciones: Oracle Free / Developer

Para laboratorios, PoC y desarrollo. Límites duros: 2 GB RAM, 12 GB de datos de usuario, 2 hilos de CPU y máximo 3 PDBs.

Incluye: motor relacional completo, JSON Relational Duality, Multitenant básico y AI Vector Search.

No incluye: Advanced Partitioning, In-Memory Column Store, Advanced Security (TDE), Database Vault, Diagnostic/Tuning Pack (AWR/ADDM), RAC/Data Guard, ni parches OPatch / soporte MOS.

Ediciones: Standard Edition 2 (SE2)

Pymes y entornos departamentales. Capada por código: máximo 2 sockets físicos y nunca más de 16 hilos de CPU.

Incluye: motor corporativo, failover pasivo (SEHA), Multitenant limitado a 3 PDBs, Data Pump y RMAN.

No incluye: Advanced Partitioning, In-Memory, TDE, Database Vault, RAC/Data Guard. Prohibido usar Diagnostic Pack (AWR) y Tuning Pack.

Ediciones: Enterprise Edition (EE)

Core bancario, telecomunicaciones, gobiernos, data warehouses masivos, ERPs globales. Sin restricciones técnicas: el único límite es financiero (terabytes de RAM, cientos de procesadores con Exadata).

Opciones avanzadas (con licencias extra): RAC, Active Data Guard, Advanced Security (TDE/Redaction), Database Vault, Diagnostic & Tuning Pack, Advanced Partitioning.

El DBA debe verificar qué ha pagado la empresa antes de activar cualquier paquete o parámetro.

Trampas del licenciamiento

  • Soft Partitioning (VMware): Oracle no reconoce VMware como límite físico. Como la VM migra (vMotion), exige licenciar todos los procesadores físicos de la granja (~$100.000 → $3.000.000 en una auditoría).
  • Shadow features: ejecutar una opción Enterprise no pagada (p.ej. AWR, índice bitmap) en SE2 deja una marca indeleble en el diccionario (dba_feature_usage_statistics).
  • Hardware desproporcionado: muchos núcleos lentos (Core Factor) = licencias carísimas y rendimiento mediocre. Mejor Scale-Up: pocos núcleos a alta frecuencia (8×4.0 GHz > 16×2.0 GHz).

Protección FinOps

-- 1. Botón de pánico: apagar acceso a Management Packs no pagados
ALTER SYSTEM SET control_management_pack_access = 'NONE' SCOPE=BOTH;

-- 2. Vista chivata: detectar opciones usadas no pagadas
SELECT name, currently_used, first_usage_date
FROM dba_feature_usage_statistics
WHERE currently_used = 'TRUE';
  • Hard Partitioning legal: Oracle Linux KVM, OVM o LPARs de IBM (barrera de contención legal).
  • Desarrollo/testing: contenedores Docker/Podman con Free/Developer.
  • Producción comercial: evita Kubernetes para el motor → Bare Metal, VMs con KVM o PaaS/DBaaS (OCI Autonomous, RDS).

OCI vs otras nubes (AWS, Azure, GCP)

  • BYOL a AWS/Azure: Oracle elimina el Core Factor 0,5 → necesitas el doble de licencias.
  • RAC: en nube pública solo funciona en OCI; en las VMs de AWS, Azure y GCP no está soportado. Matiz real: los servicios Oracle Database@Azure/AWS/Google Cloud sí permiten RAC porque son Exadata operada por Oracle dentro de esos centros de datos. Para el examen, quédate con lo de los apuntes.
  • Exadata Cloud Service: fusiona almacenamiento de red + BD a nivel hardware (analítica pesada en milisegundos).
  • License Included en OCI: gasto operativo (OpEx) por horas; el riesgo de licencia lo asume el proveedor.

TNS, Listener y cadena de conexión

Oracle Net Services: capa de red propietaria (datos cifrados entre cliente y servidor). TNS = el "DNS interno" de Oracle: tnsnames.ora traduce un alias (ej. PROD_DB) en Host (IP) + Puerto (1521) + Service Name.

Listener (tnslsnr): demonio independiente que escucha en el 1521 como recepcionista: verifica el servicio, conecta el cliente con un server process y se desentiende.

Regla SRE: si el Listener muere, las conexiones establecidas siguen funcionando; solo los nuevos usuarios no podrán entrar.
sqlplus admin/miClave@192.168.1.50:1521/PDB_Ventas
  1. Cliente empaqueta la solicitud (SQLcl / SQL*Plus).
  2. El paquete viaja por TCP/IP hasta el host.
  3. El Listener intercepta la petición en el puerto 1521.
  4. Resolución lógica: verifica que la PDB existe y está abierta.
  5. El SO crea un Server Process dedicado.
  6. Handoff: el Listener se desconecta de la conversación.
  7. El Server Process se "sumerge" en el contexto de la PDB (solo ve esa oficina).
  8. Autenticación contra SYS.USER$ de esa PDB (ORA-01017 si el hash no coincide).
Un ataque de fuerza bruta no ataca al Listener: ataca a los Server Processes, que son quienes validan credenciales.

Sección 2.2 - Navegación por el Ecosistema Oracle

Plano físico vs plano lógico: Instance y Database

ConceptoDónde viveAuditarQué observar
InstanceRAM (SGA/PGA + procesos). Muere al apagar el servidor.SELECT * FROM v$instance;status OPEN/MOUNTED.
DatabaseDisco (datafiles, control files, redo logs). Es eterna.SELECT * FROM v$database;log_mode (ARCHIVELOG).
  • Una instancia NO monta dos bases de datos a la vez.
  • Una base de datos SÍ puede ser montada por varias instancias: eso es RAC.

Service, Session y Schema

  • Service: abstracción de red que usa el Listener para saber a qué contenedor dirigirte. Auditoría: v$services.
  • Session: interacción activa cliente-instancia; consume RAM. Auditoría: v$session (sid, serial#, username, status).
  • Schema: Schema = Usuario (regla de oro). Es el contenedor lógico propietario de los objetos, NO es un disco. Auditoría: dba_users.
Schema vs Tablespace: el Schema define quién es el dueño; el Tablespace define en qué disco se guarda. Un usuario puede tener tablas en varios tablespaces; no se contienen mutuamente.

Arquitectura Multitenant: CDB y PDB

  • CDB (Container Database) = el edificio: infraestructura principal que gestiona memoria, instancia y procesos. Auditoría: SELECT cdb FROM v$database; (YES).
  • PDB (Pluggable Database) = la oficina: base conectable, lógicamente aislada. Auditoría: SHOW CON_NAME; y SELECT con_id, name, open_mode FROM v$pdbs;.

El diccionario se dividió: dentro de una PDB, DBA_USERS solo muestra esa oficina. Desde CDB$ROOT usa CDB_USERS siempre con CON_ID.

Trampa clásica: si omites CON_ID en CDB_USERS verás varios "ADMIN" sin saber a qué PDB pertenece cada uno.

Modelo de 2 niveles: un CDB (padre) aloja PDBs (hijos). Un CDB no puede estar dentro de otro CDB y una PDB no puede contener PDBs.

Application Container (modelo de 3 niveles, 12c R2)

Resuelve el problema SaaS: parchear una sola vez el Application Root actualiza la estructura de todos los clientes.
  1. CDB (contenedor raíz).
  2. Application Root (PDB especial contenedor: instala la estructura maestra, ej. tabla Facturas).
  3. Application PDBs (PDBs de clientes que heredan la estructura del Root).

Sección 2.3 - Herramientas de Oracle

Tres familias de herramientas

  • CLI (supervivencia y automatización): innegociables para CI/CD y recuperación.
  • IDE / GUI (desarrollo y modelado): orientadas al desarrollador PL/SQL y analistas.
  • Observabilidad y gestión de flota: monitoreo centralizado de cientos de BDs.
Máxima SRE: "Las interfaces gráficas son para tiempos de paz; la línea de comandos para tiempos de guerra." Con memoria agotada o red saturada, las GUIs no conectan; el CLI es el único salvavidas.

CLI y herramientas de desarrollo

  • SQL*Plus: CLI nativo clásico, integrado con el motor. Sin autocompletado ni colores, pero garantía absoluta.
  • Oracle SQL Developer: IDE gráfico gratuito en Java. PL/SQL, depuración paso a paso, EXPLAIN PLAN, modelado ER e ingeniería inversa.
  • Database Actions (antes SQL Developer Web): experiencia de cero instalación en navegador, basada en ORDS, integrada por defecto en OCI y Autonomous.

Database Actions

  • Performance Hub: métricas en tiempo real, historial ASH, SQL lentas, eventos de espera CPU/I/O.
  • AutoREST: exponer tablas/vistas/procedimientos como endpoints REST (GET/POST/PUT/DELETE) con seguridad OAuth 2.0.
  • SODA / JSON Studio: la BD relacional como almacén de documentos tipo MongoDB, con consultas Query by Example (QBE).
  • Data Modeler + Data Studio: ER y DDL; carga de CSV/Excel/JSON/Avro.
  • Wallets (mTLS): descarga de carteras de seguridad, requisito estricto para conectar a Autonomous.

Oracle Enterprise Manager (OEM / Cloud Control)

La torre de control: gestión 1 a N (SQL Developer/DB Actions son 1 a 1). Requiere arquitectura OMS + base de datos de repositorio + agentes.

Tareas que SOLO se hacen con OEM:

  • Fleet Patching: orquestar parches (RU/RUR) a cientos de servidores.
  • AWR/ADDM global: comparar rendimiento de toda la flota (hoy vs. hace meses).
  • Capacity Planning: proyectar tendencias de crecimiento.
  • Compliance Framework: auditoría contra CIS, PCI DSS, STIG.

Administración y soporte: OPatch y AWR

  • OPatch: inyecta los Release Updates (RUs) en los binarios para cerrar vulnerabilidades (CVEs), con mínimo downtime (parcheo rodante en RAC).
  • AWR (Automatic Workload Repository): la "caja negra" del motor; fotografías (snapshots) horarias del estado de memoria, CPU y eventos de espera.

Sección 2.4 - Oracle como "Piedra de Rosetta"

80% commodity + 20% diferenciador

El 80% del funcionamiento de una BD relacional es estándar universal (commodity); las empresas pagan Oracle por el 20% diferenciador.

Conocimiento transferible (a cualquier motor):

  • Árboles B y la física de la búsqueda
  • Transacciones ACID
  • Optimizador basado en coste (CBO) y estadísticas
  • Separación lógico-física
  • Diccionario de datos
  • Niveles de aislamiento y bloqueos

Diferenciadores absolutos de Oracle (intentar replicarlos igual en otros motores es un error de diseño):

  • Undo Tablespace + Flashback
  • Redo Logs físicos (base de RAC y Active Data Guard)
  • PL/SQL como motor de cómputo cercano al dato
  • Arquitectura Multitenant nativa (unplug/plug)
  • Consistencia de lectura a nivel de sentencia

Por qué las empresas pagan la licencia

  • Alta disponibilidad activo-activo real (RAC)
  • Concurrencia sin "basura" (Undo Tablespace)
  • La máquina del tiempo (Flashback Database / Query)
  • BD convergente (Duality Views + AI Vector)
  • Gobernanza paranoica (Database Vault)
"Las empresas no compran Oracle por SELECTs más bonitos": compran los diferenciadores de misión crítica. No se debe elegir marca por tradición, sino por la topología de la carga y las exigencias del negocio.

Sección 2.5 - Ruta Formativa y Certificación 26ai

Portafolio SRE de élite

  • Runbooks: scripts Bash/SQLcl para automatizar despliegues de PDBs.
  • Análisis forense: casos documentados interpretando AWR reales.
  • Simulaciones de desastres: recuperación con RMAN (bitácoras).
  • Casos de IA: AI Vector Search combinando datos relacionales con LLMs.

Pilares estratégicos para llegar a SRE

  1. Romper en local, certificar en global: destruye tu BD a propósito en docker (Free) para aprender a repararla.
  2. Construcción de evidencia técnica: tu portafolio SRE (bitácoras, repos git, Golden Image desplegada en segundos).
  3. Aprovechar el ecosistema: Oracle Academy (Student Hub, vouchers) → Pearson VUE (validación externa) → Oracle University (insignia digital en LinkedIn).
  4. Entrenar el triaje forense, no la memoria: los exámenes presentan un servidor colapsado y exigen elegir la solución arquitectónicamente viable; estudia el diccionario (DBA_/V$) entendiendo el porqué.
  5. Evolucionar hacia el valor del negocio: datos seguros, protección anti-ransomware e inteligencia competitiva (AI Database).
