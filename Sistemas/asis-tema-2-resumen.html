1. Fundamentos: abstraer recursos

Virtualizar ≠ agregar

VIRTUALIZACIÓN: 1 computador físico → parece → N computadores
AGREGACIÓN/GRID: N computadores físicos → parecen → 1 computador

Virtualización: tecnología software que abstrae recursos dando acceso lógico a recursos físicos. Quien los usa no necesita conocer el hardware real, y varios SO pueden correr sobre el mismo equipo.

No es reciente: el Atlas (1962) ya repartía procesador y almacenamiento entre terminales, partiendo disco, memoria y cómputo sin interferencias.

Recursos virtualizables y los dos conceptos clave

Sobre un host se virtualizan CPU, memoria, almacenamiento y red. Ej. servidor de 16 núcleos / 64 GB / 2 TB repartido en VMs de 4-8 vCPU, 16-32 GB y cientos de GB: cada VM los percibe como propios.

  • VM: contenedor software aislado con hardware simulado + SO + aplicaciones. Para el SO guest es como un ordenador propio.
  • Hipervisor (VMM): capa que desvincula las VM del host, reparte recursos dinámicamente y gestiona el acceso al hardware. Corre sobre el hardware o sobre un SO anfitrión.
VM1 · VM2 · VM3 → HIPERVISOR → HARDWARE
VM = ordenador virtual. Hipervisor = quien los administra y reparte el hardware.

Virtualización ≠ Cloud Computing

VirtualizaciónCloud
Qué esTecnologíaMetodología
ObjetivoMúltiples entornos sobre un físicoRecursos automatizados bajo demanda
GestiónEl admin gestiona hipervisor y VMMucho se automatiza vía APIs
RecursosConjunto particularConjunto variable según necesidad
La virtualización posibilita el cloud, pero no equivale a él.

2. Tipos de virtualización

De plataforma: emulación, paravirtualización y completa

  • Emulación nativa: replica una arquitectura sobre otra (guest → HW virtual → emulador → HW real). Vale aunque el software espere otra arquitectura.
  • Paravirtualización: el hipervisor expone hypercalls y el guest modificado colabora en vez de emularlo todo.
  • Completa: el guest no necesita modificarse ni colaborar explícitamente.
Para = el guest participa. Completa = el guest no se modifica.

SO, recursos, aplicaciones y escritorio

  • De SO: entornos independientes sobre el mismo kernel del host. Clave para entender contenedores.
  • De recursos: abstrae un recurso, no el computador (memoria virtual con swap de Linux, red con VPN, RAM combinada en red).
  • De aplicaciones: encapsula la app tras una capa intermedia para portabilidad y compatibilidad. Ej. Wine, JVM, CLR (.NET).
  • De escritorio: el escritorio vive en un servidor remoto y se usa desde PC, portátil o móvil. Ej. Citrix.

3. Cómo funciona y tipos de hipervisor

Por software o asistida por hardware

La asistida usa extensiones de CPU (Intel VT, AMD-V). El hipervisor corre en ring -1, más privilegiado que el SO guest (ring 0) y las apps (ring 3): la CPU captura operaciones privilegiadas del guest, el VMM las gestiona y el guest sigue creyendo estar en ring 0.

Tipo 1 vs Tipo 2 (fundamental)

Tipo 1 (bare metal)Tipo 2
Dónde correDirecto sobre hardwareSobre un SO host
EjemplosVMware ESXiWorkstation, VirtualBox, Parallels, VirtualPC
BalanceMayor rendimientoMás compatibilidad/funciones, pero menor rendimiento y estabilidad
Tipo 1 = hipervisor sobre hardware. Tipo 2 = hipervisor sobre SO.

FicheroContiene

.nvramEstado de la BIOS

.vmdkDisco virtual (uno o varios ficheros; s###.vmdk por trozos, f###.vmdk si se reserva todo el espacio)

El .vmdk parece un disco (C:\, /) para la VM, pero físicamente son archivos en el host. El snapshot permite recuperar un estado anterior.

5. Por qué virtualizar: ventajas e inconvenientes

El problema: servidores infrautilizados

Cuatro servidores al 10/15/8/20 % consumen electricidad, espacio, refrigeración y mantenimiento casi para nada. Virtualizando se consolida: esas cuatro cargas viven como VMs en un físico con alta utilización.

Otras razones: falta de espacio en CPD, abstraer almacenamiento, eficiencia energética, menos coste de administración, monitorización centralizada, aprovisionamiento automático, backups y restauración simples, redundancia, alta disponibilidad y rendimiento. Los servicios modernos aspiran a 24×365.

Ventajas, alta disponibilidad e inconvenientes

  • Consolidación, administración simple (clonar, desplegar, copiar, restaurar), redundancia repartida, menos costes, backups fáciles y eficiencia energética.
  • Alta disponibilidad: si cae el host A, la VM del servicio pasa al host B gracias a separar máquina lógica y física.
Coste: capa adicional → pérdida de rendimiento (App → SO guest → hipervisor → HW), y los recursos físicos siguen siendo finitos: hay que dimensionar bien el host. La hiperconvergencia (cómputo + almacenamiento + red + virtualización gestionados juntos) busca simplificar aún más.

6. De la virtualización al cloud: AWS

La cadena y el ejemplo

HARDWARE → VIRTUALIZACIÓN → RECURSOS VIRTUALES → AUTOMATIZACIÓN → CLOUD

La virtualización abstrae; el cloud añade automatización y consumo bajo demanda. AWS lo ejemplifica: el usuario solicita computación, almacenamiento o red y consume recursos lógicos sin comprar el servidor físico.

7. Contenedores y Docker

VM vs contenedor

VMContenedor
Virtualiza una máquina (SO guest propio)Aísla el entorno compartiendo el kernel
Más pesada, más recursos, arranque más lentoMás ligero, menos recursos, arranque más rápido
VM → virtualiza hardware. Contenedor → aísla apps compartiendo kernel.

Docker encapsula app + dependencias + configuración en un entorno reproducible: adiós al «en mi ordenador funciona».

Arquitectura y la cadena Dockerfile → imagen → contenedor

Usuario → Docker Client → Engine/Daemon → Imágenes / Contenedores
Registry ──pull──► Imagen ──run──► Contenedor
Dockerfile ──build──► Imagen ──run──► Contenedor
  • Imagen: plantilla con lo necesario para crear contenedores (una imagen → muchos contenedores, ej. nginx ×2).
  • Contenedor: instancia en ejecución (procesos, filesystem, config, red). Analogías: clase→objeto, receta→plato.
  • Dockerfile: instrucciones de construcción (FROM, WORKDIR, COPY, RUN, EXPOSE, CMD). La idea más importante de Docker.
  • Capas: imagen base + runtime + dependencias + app; se reutilizan y distribuyen fácil.

Persistencia: el contenedor es efímero, los datos no

El ciclo es crear → ejecutar → detener → eliminar → recrear. Vida del contenedor ≠ vida de los datos: si una BBDD vive solo en el filesystem interno, borrar el contenedor es un problema.

Solución: volúmenes. El contenedor monta /datos en un volumen; al eliminar el contenedor los datos se mantienen y un contenedor nuevo los reutiliza.

Ventajas Docker: ligereza, rapidez, portabilidad, aislamiento, reproducibilidad, automatización y eficiencia sobre el mismo host.

Hilo conductor del Tema 2

Servidores desaprovechados → abstraer CPU/RAM/disco/red → hipervisor con múltiples VM → consolidación y eficiencia → automatización (cloud, AWS) → aislamiento por kernel (contenedores) → Docker: Dockerfile, imagen-plantilla, contenedor-instancia y volúmenes para persistir.
